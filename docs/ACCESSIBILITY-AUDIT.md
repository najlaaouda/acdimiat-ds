# Acadimiat — Accessibility Audit (WCAG 2.1 Level AA)

> **الحالة:** فحص فقط. لم يُعدَّل أي ملف إنتاجي.
> **النطاق:** Admin Dashboard UI.
> **المعيار:** WCAG 2.1 Level AA كحدّ أدنى.
> **طريقة الفحص:** تحليل ثابت للكود (grep/awk) + حساب نسب التباين رياضيًا (صيغة WCAG relative luminance). **لم يُجرَ فحص ديناميكي بالمتصفح ولا اختبار بقارئ شاشة** — بعض البنود تحتاج تحقّقًا يدويًا لاحقًا، وهي مُعلَّمة بـ 🔍.

### A-01 · مؤشّر التركيز مُخفى افتراضيًا في التطبيق كله

| البند | التفصيل |
|---|---|
| **المعيار** | WCAG 2.1 **2.4.7 Focus Visible (AA)** |
| **الخطورة** | 🔴 **حرجة — Blocker** |
| **المكوّن المتأثّر** | **كل عنصر تفاعلي في التطبيق** — 1283 زرًا، 1280 حقلًا، كل الروابط والقوائم والتبويبات |
| **الموقع** | `src/styles.scss:1850-1856` + `src/app/services/accessibility.service.ts:26` |

**الكود:**

```scss
html:not([data-a11y-focus="default"]):not([data-a11y-focus="high"]) *:focus,
html:not([data-a11y-focus="default"]):not([data-a11y-focus="high"]) *:focus-visible,
html:not([data-a11y-focus="default"]):not([data-a11y-focus="high"]) *:focus-within {
  outline: none !important;
  box-shadow: none !important;
}
```

```ts
focusIndicator: 'off', // Hidden by default; user activates via FAB
```

**لماذا هي مشكلة:**

القيمة الافتراضية `'off'` تعني أن المحدّد `html:not([data-a11y-focus="default"]):not([data-a11y-focus="high"])` يطابق دائمًا عند أول زيارة. النتيجة: **مستخدم لوحة المفاتيح لا يرى أين هو**. والـ `!important` على المحدّد الشامل `*` يُبطل أي focus ring يكتبه أي مكوّن — بما فيها الـ 202 استخدامًا الصحيحة لـ `:focus-visible`.

WCAG **لا يقبل** جعل هذا خيارًا يفعّله المستخدم: المعيار يشترط أن يكون وضع لوحة المفاتيح مرئيًا، والمستخدم الذي يحتاجه غالبًا لا يستطيع الوصول إلى زر التفعيل نفسه بلوحة المفاتيح — **مفارقة دائرية**.

**الحل الموصى به:**

1. تغيير الافتراضي إلى `'default'` في `accessibility.service.ts:26`.
2. قلب منطق CSS: التركيز **ظاهر دائمًا**، والـ FAB يقدّم `high` (أوضح) و — إن لزم — `subtle`، **بلا خيار `off` إطلاقًا**.
3. اعتماد token واحد:

```css
*:focus-visible {
  outline: var(--ap-focus-ring-width) solid var(--ap-color-focus-ring);
  outline-offset: var(--ap-focus-ring-offset);
}
```

4. الإبقاء على `:focus:not(:focus-visible) { outline: none }` — هذه القاعدة صحيحة.

**التحقّق:** التنقّل بـ Tab عبر الصفحات العشر الأكثر استخدامًا في متصفّح نظيف (بلا localStorage) — كل محطّة توقّف مرئية.

### A-02 · `.btn` يُلغي التركيز على 970 زرًا

| البند | التفصيل |
|---|---|
| **المعيار** | 2.4.7 Focus Visible (AA) |
| **الخطورة** | 🔴 حرجة |
| **المكوّن** | كل زر Bootstrap (970 استخدامًا لـ `.btn`) |
| **الموقع** | `src/assets/css/panel-style.css:3426` |

```css
.btn:hover, .btn:focus, .btn:active, .btn.active {
    outline: 0 !important;
    box-shadow: none;
}
```

**لماذا هي مشكلة:** طبقة إخفاء ثانية مستقلّة عن A-01. حتى بعد إصلاح A-01، هذه القاعدة تبقى فاعلة لأنها `!important` وتصيب أكثر نمط أزرار انتشارًا.

**الحل:** حذف `:focus` من قائمة المحدّدات، والإبقاء على `:hover`/`:active` فقط. ثم إضافة `.btn:focus-visible { outline: var(--ap-focus-ring…) }` في طبقة الـ foundations الجديدة (تُحمَّل بعده فتعلو عليه بالترتيب).

### A-04 · الحقول بلا ربط دلالي بين الـ label والـ input

| البند | التفصيل |
|---|---|
| **المعيار** | 1.3.1 Info and Relationships (A) · 3.3.2 Labels or Instructions (A) · 4.1.2 Name, Role, Value (A) |
| **الخطورة** | 🔴 حرجة |
| **المكوّن** | كل النماذج — 92 مكوّن dialog + كل صفحات الإعدادات والمنتجات |

| القياس | العدد | النسبة |
|---|---|---|
| `<input>` | **1280** | — |
| `<input id="…">` | **24** | **1.9 %** |
| `<label>` | 1329 | — |
| `<label for="…">` | **166** | **12.5 %** |
| `aria-required` | **1** | 0.08 % |

**لماذا هي مشكلة:** قارئ الشاشة يقرأ الحقل كـ "مربّع تحرير" بلا اسم. المستخدم لا يعرف ما يُدخل. والنقر على النص لا ينقل التركيز إلى الحقل (فقدان مساحة نقر لذوي الإعاقة الحركية).

**ملاحظة تخفيف:** بعض الحالات يغطّيها `mat-form-field` (14 فقط) أو التداخل (`<label><input></label>`) — لكن الفحص يُظهر أن النمط السائد هو label شقيق بلا ربط.

**الحل:** توليد `id` تلقائيًا داخل `<ap-field>` وربطه — وهو **تغيير بصفر أثر بصري**، ويُنجَز بالترحيل إلى مكوّن الحقل الموحّد.

### A-05 · رسائل الخطأ غير معلَنة وغير مربوطة، وبتباين ساقط

| البند | التفصيل |
|---|---|
| **المعيار** | 3.3.1 Error Identification (A) · 1.4.3 Contrast (AA) · 4.1.3 Status Messages (AA) |
| **الخطورة** | 🔴 حرجة |
| **المكوّن** | كل النماذج — 256 رسالة خطأ |

| النمط | العدد | اللون | التباين | يمرّ؟ |
|---|---|---|---|---|
| `.form-errors` | **133** | `#f00a` → فعليًا `#ff5555` | **3.14:1** | ❌ |
| `.invalid-feedback` | **95** | `#ff4c41` | **3.30:1** | ❌ |
| `.form-errors` (الحدّ) | 133 | `#f008` → `#ff7777` | **2.57:1** | ❌ (المطلوب 3:1) |
| محلية (`field-error`, `modal__error`…) | ~28 | متغيّر | — | 🔍 |

**ثلاث مشاكل مجتمعة:**

1. **التباين ساقط** في النمطين الرئيسيين.
2. **لا `role="alert"` ولا `aria-live`** في أي منها → الخطأ لا يُعلَن عند ظهوره.
3. **`aria-invalid` مستخدم 10 مرات** من 1280 حقلًا → الحقل نفسه لا يُعلَن كخاطئ.
4. **الخطأ منقول باللون وحده** — لا أيقونة ولا نصّ دالّ في معظم المواضع (مخالفة 1.4.1).

**مشكلة إضافية مرصودة:** `.is-invalid` مطبَّق على **9** حقول فقط مقابل **95** رسالة `.invalid-feedback` → في 86 حالة **يظهر النص الأحمر والحقل بلا أي تمييز بصري**.

**الحل:** انظر [`FORM-COMPONENTS-SPEC.md`](./FORM-COMPONENTS-SPEC.md) §9.2 — نمط واحد بـ `role="alert"` + `aria-invalid` + `aria-describedby` + أيقونة + `--ap-red-700` (6.79:1).

### A-06 · أزرار الأيقونات بلا اسم متاح

| البند | التفصيل |
|---|---|
| **المعيار** | 4.1.2 Name, Role, Value (A) · 2.4.4 Link Purpose (A) |
| **الخطورة** | 🔴 حرجة |
| **المكوّن** | 12 عائلة icon-button (~90 استخدامًا) + أزرار الجداول |

النمط السائد:

```html
<button class="icon-btn" (click)="delete()"><i class="fa fa-trash"></i></button>
```

الأيقونة خطّية (`::before` على `<i>`) → قارئ الشاشة يقرأ **"زر"** بلا أي وصف، أو يقرأ محرف Private Use Area عشوائيًا.

**الحل:** `aria-label` إلزامي في مكوّن `<ap-button icon-only>` — يرفض التصيير بدونه في وضع التطوير. و`aria-hidden="true"` على كل `<i>` زخرفية.

🔍 **يحتاج فحصًا يدويًا:** بعض المواضع تستخدم `matTooltip` (125 استخدامًا) الذي يولّد `aria-describedby` — لكنه **وصف لا اسم**، وغير كافٍ وحده.

| الخطورة | 🟡 متوسطة |

التطبيق يوفّر تكبير خط بخمسة مستويات عبر `html { font-size }` — لكن **43 % من أحجام الخط بالبكسل** (`13px`, `12px`, `11px`, `14px`…). هذه لا تتأثّر بالميزة إطلاقًا.

**النتيجة:** ميزة إمكانية وصول موجودة تعمل جزئيًا، ما قد يمنح انطباعًا زائفًا بالامتثال.

**الحل:** كل `font-size` بالـ `rem` عبر `--ap-font-size-*`.

### A-17 · المسافات بالـ rem تنهار مع تكبير الخط

| المعيار | 1.4.10 Reflow (AA) |
|---|---|
| الخطورة | 🟡 متوسطة |

`0.35rem`, `0.55rem`, `0.65rem`, `0.85rem` (~120 استخدامًا) تنمو مع تكبير الخط بينما جاراتها بالبكسل لا تنمو → انهيار محاذاة عند 137.5 %.

🔍 **يحتاج فحصًا بصريًا** عند كل مستوى تكبير.

**الحل:** المسافات بالبكسل حصرًا (`--ap-space-*`).

### A-18 · الحالة المعطَّلة بشفافية مفرطة

| المعيار | جودة — العناصر المعطَّلة مستثناة من 1.4.3، لكن القابلية للقراءة مطلوبة |
|---|---|
| الخطورة | 🟡 متوسطة |

10 قيم شفافية للحالة المعطَّلة: `0.35` (3 مواضع)، `0.4` (8)، `0.45`، `0.5` (14)، `0.55` (24)، `0.6` (17)، `0.65` (8)، `0.7`، `0.72`، `0.9`.

عند `0.35`: نص `slate-900` يصبح **2.22:1** — غير مقروء عمليًا.

**الحل:** قيمة واحدة `--ap-button-disabled-opacity: 0.5` (تعطي 3.41:1 للنص الأساسي)، أو الأفضل: ألوان معطَّلة صريحة بدل الشفافية.

## 7. ملاحظة على وثيقة `ACCESSIBILITY_TREE_ROADMAP.md`

الوثيقة الموجودة في جذر المشروع تقول: **"95 % مكتمل — المراحل 2 إلى 7 منجزة"**.

الفحص الحالي يُظهر أن ما أُنجز هو **البنية التحتية** (الخدمات، الـ FAB، التفضيلات، الاختبارات، التوثيق) — وهو إنجاز حقيقي. لكن **طبقة التطبيق على مكوّنات الواجهة الفعلية** (الربط الدلالي، وضوح التركيز، التباين) ما زالت في بدايتها.

النسبة الأدقّ بمعيار AA على واجهة الـ Admin: **قريبة من 55–60 %**، مع 6 مشاكل حرجة قائمة. وهذا ليس تراجعًا عن الوثيقة السابقة بل تقييم لنطاق مختلف: تلك تقيس البنية، وهذه تقيس المكوّنات.
